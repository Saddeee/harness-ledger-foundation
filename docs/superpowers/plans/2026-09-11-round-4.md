# Round 4 Implementation Plan — Phase A (analysis), Phase C + 4b (outcomes, deprecation), Phase D (small gaps)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Phase B (paired test) gets its own plan after this one ships.

**Goal:** Harness turns synced chats into proposals with the user's own LLM (API key or Claude Code subscription) under a token budget, tracks how each live rule performs on real builds, proposes retiring rules that hurt, contradict or go unused, and closes three small gaps (evidence links, Inbox count/unread, Retire).

**Spec:** `docs/superpowers/specs/2026-09-11-round-4-analysis-proof-outcomes.md` (§2, §4, §4b, §5). Design detail and prompt drafts: `docs/superpowers/specs/explorations/analysis-pipeline.md` (§1 provider shapes, §4 prompts) and `explorations/evidence-notifications-retire.md`.

## Phase A — Analysis pipeline

**Migration ownership:** Task A0 alone writes migration v9 with EVERY round-4 schema change (llm_calls columns, settings key changes, `message_classifications`, `analysis_requests`, `analysis_runs`, `rule_health`, `rules.scope_tags_json`, `retire_proposals`). No other task edits `migrations.ts`; they only add store functions in delimited blocks.

### Task A0 — Provider client (`harness/src/llm/`)
Files: `harness/src/llm/{types,prices,budget,openai,anthropic,google,claude-code,index}.ts`; `harness/src/llm-keys.ts` gains `getKey(provider): string | null`; migration v9 (`llm_calls` gains `estimated_tokens INTEGER`, `run_id INTEGER NULL`; settings key `llm_monthly_token_budget` default "2000000", validated 100000–50000000; remove `llm_monthly_budget_usd` from defaults/validation and migrate: delete that settings row if present); store: `sumLlmTokensThisMonth()`, `sumLlmCostThisMonth()` unchanged. Tests: `harness/test/llm.test.ts`.
Interfaces:
```ts
export type LlmRole = "classifier" | "miner" | "reviewer" | "proposer";
export type LlmProvider = "openai" | "anthropic" | "google" | "claude_code";
export type LlmRequest = { role: LlmRole; system: string; user: string; schema: object; schemaName: string; maxOutputTokens?: number; runId?: number };
export type LlmResult<T> = { json: T; provider: LlmProvider; model: string; tokensIn: number; tokensOut: number; costUsd: number | null; latencyMs: number };
export type CallLlm = <T>(req: LlmRequest) => Promise<LlmResult<T>>;
export function createCallLlm(deps?: { fetchFn?: typeof fetch; exec?: (cmd: string, args: string[], input: string) => Promise<{ stdout: string; code: number }> }): CallLlm;
export class LlmBudgetExceeded extends Error {}; export class LlmKeyMissing extends Error {}; export class LlmProviderUnavailable extends Error {}
```
Behaviour: provider+model per role from `llm_models` (fallback `llm_provider`); key from `getKey` (API providers) or none (`claude_code`); estimate tokens as `ceil((system+user).length/4) + maxOutputTokens(default 1500)`; refuse with `LlmBudgetExceeded` when `sumLlmTokensThisMonth() + estimate > budget`; call; parse JSON strictly (retry once with "Return only JSON matching the schema" on parse failure); log to `llm_calls` (tokens, cost from `prices.ts` — null for claude_code); `claude_code` adapter runs `claude -p --output-format json --model <model> --system-prompt <system>` (verify flag names with `claude --help` in the task; if `--system-prompt` is unavailable, prepend the system text to the prompt) with the user text on stdin, parses `result` as JSON and `usage` tokens; `LlmProviderUnavailable` when `claude --version` fails. Exact HTTP shapes for the three API providers are in the exploration doc §1; test each against a mocked `fetch` asserting URL, headers (key never logged), body flags for JSON mode, and response parsing. Budget guard and key-missing paths tested.

### Task A1 — Classify and segment (`harness/src/analysis/classify.ts`, `segment.ts`)
Interfaces: `classifyPending(callLlm, opts: { limit: number }) → { classified: number }` — selects user `history_items` (kind message) not yet classified (new table `message_classifications(history_item_id PK, classification, tags_json, summary, run_id, created_at)` in migration v9), builds context = previous 3 messages (assistant text via `lovableReplyText`-equivalent in harness: port the regex to `harness/src/analysis/reply-text.ts`), truncates each message to 1,500 chars, calls the classifier with the JSON schema `{ classification: new_task|correction|question|approval|other, tags: string[] (from the fixed taxonomy), summary: ≤120 chars }`. `segmentEpisodes(projectId) → { created: number, updated: number }` — deterministic, no LLM: walk classified user messages in time order; a `new_task` starts an episode (`createTaskEpisode` with title = summary, `provenance` per the enum), following `correction`s attach as evidence (`task_episode_evidence`), until the next `new_task`; idempotent via a `history_item_id → task_episode_id` link (add `history_item_id` linkage through the existing evidence table). Tests with a scripted history and a fake `callLlm` returning canned classifications: episode boundaries, idempotency (second run creates nothing), question-only messages create no episode.

### Task A2 — Mine and dedupe (`harness/src/analysis/mine.ts`, `similarity.ts`)
Interfaces: `mineEpisodes(callLlm, opts: { limit: number }) → { proposed: number; skippedDuplicate: number; skippedNoCorrection: number }` — for episodes with ≥1 correction and no `correction_candidates` row, call the miner with the episode (request, corrections with ids, assistant summaries), project name, and the texts of live rules; schema `{ propose: boolean, instruction: ≤300 chars imperative, scope: project|workspace, prediction, failure_signature: kebab-case, evidence_message_ids: string[], confidence: 0–1, contradicts_rule_id: number|null, duplicate_of_rule_id: number|null }`; validate evidence ids exist in the episode; Dice similarity (`similarity.ts`, bigram) vs live rule texts: ≥0.8 skip as duplicate, 0.6–0.8 only if the model also said duplicate; write via `createCorrectionCandidate` (classification from the first correction, `is_correction: true`, `reusable: true`, `proposed_scope`, summary = prediction, `confidence`, `evidence_reason`), `createLearning`, `createRule` (state `proposed`) exactly as the MCP tools do (read `mcp-server.ts` handlers). Record `contradicts_rule_id` into `rule_health.contradicted_by_rule_id` (table from Task C1; if C1 has not landed, write to a `pending_contradictions` JSON setting and let C1 migrate it — simpler: order C1 before A2). Tests: scripted episode → one proposal rendered by `listImprovements()` identically to a hand-made one; near-duplicate skipped; no-correction episode never calls the miner; invalid evidence id → proposal rejected and logged.

### Task A3 — Analysis runs and trigger
Migration v9 additions: `analysis_requests(id, requested_at, status requested|running|done, run_id)`, `analysis_runs(id, started_at, finished_at, ok, error, counts_json, tokens, cost_usd)`. `harness/src/analysis/run.ts`: `runAnalysis(callLlm, kind) → { runId, ok, counts, error? }` = classify → segment (per allowed project) → mine, each capped (200 calls per run total), never throws, consumes open requests. Executor loop: a tick with an open `analysis_requests` row runs `runAnalysis` (independent of the Lovable connection); `--analyse` CLI flag runs one. Route `executor.ts`: GET adds `analysis: { last_run, running, tokens_this_month, token_budget, cost_usd_this_month | null, provider_ready: { ok: boolean; reason?: string } }` (provider_ready checks key presence or `claude --version`); POST `analyse_now`. Client types. Tests: run with fake callLlm consumes the request and records counts; provider-not-ready run finishes with `ok:false` and the reason.

## Phase C + 4b — Outcomes and deprecation

### Task C1 — rule_health computation
Migration v9: `rule_health(rule_id PK, applicable_tasks, helped, hurt, last_applicable_at, contradicted_by_rule_id, unused_since, status healthy|watch|retire_suggested|snoozed, snoozed_until, computed_at)`; settings `rule_unused_after_days` ("60", 7–365). `harness/src/analysis/health.ts`: `recomputeRuleHealth() → { rules: number; suggested: number }` — for each live (`active`) rule: episodes started after the rule's first `written_at` in the rule's project (all projects for workspace scope), applicable when the episode's tags (union of its messages' classification tags) overlap the rule's scope tags or the rule has `general` (rules get `scope_tags_json` in v9, defaulting to `["general"]`; the miner from A2 sets them); hurt when an applicable episode has a correction whose summary matches the failure signature (equal) or Dice ≥ 0.7 vs the rule's prediction; helped otherwise; unused when `last_applicable_at` older than the setting; `retire_suggested` when `applicable_tasks ≥ 3 && hurt > helped` or contradicted or unused, unless snoozed. Called at the end of every sync run and analysis run. Tests with scripted episodes and classifications.

### Task C2 — Retirement proposals in the Inbox + Retire/Keep/Re-add
Data: a retirement proposal is a new improvement kind: `retire_proposals(id, rule_id, reason hurt|contradiction|unused, evidence_json, status open|retired|kept, created_at, decided_at)`; `listImprovements()` returns them as `kind: "retire"` items (title "Retire: <instruction>", body with the health line and reason, evidence = the hurt episodes' correction messages); actions `retire` (rule `retired`, recompose managed block for the target, stage a pending version with reason "retired rule N", improvement group "Retired"), `keep` (snooze 30 days), `readd` (rule `approved`, stages a write). Manual "Retire" on the Instructions page uses `retire` directly. `IMPROVEMENT_GROUPS` gains "Retired" after "Reverted". Executor `stageApprovedWrites` and `max_active_rules` ignore retired rules. UI: `DecisionCard` renders `kind: "retire"` with buttons Retire / Keep; Instructions page: health line under each live rule and a Retire button; retired rules listed collapsed with Re-add. Tests: data layer and structural.

### Task C3 — Health line on cards and the Inbox count
`Improvement.health` = `{ applicable_tasks, helped, hurt, last_applicable_at }` for live rules; card line "Since added: 4 tasks · 3 helped · 1 repeat correction · from real builds"; the sidebar "Inbox" label shows a count badge of pending + open retire proposals (from a lightweight `GET improvements?count=1` or the existing list); `inbox_last_seen_at` setting set when the Inbox mounts; cards newer than it get a small "New" chip.

## Phase D — Small gaps

Each quoted message gets "Open in Lovable" → `https://lovable.dev/projects/<project_id>` (deep link with `?message=<external_id>` attempted; a note in the report says whether Lovable honoured it in a manual check by the owner; the link degrades to the project). `MessageBlock` change + test.

### Task D2 — Browser notification opt-in
Settings › Notifications: "Notify me in this browser when a new proposal or retirement suggestion arrives" (Notification API permission flow; stored in localStorage as a per-browser convenience); the app polls the improvements count every 60 s while open and fires one notification per new item. Test structural only.
