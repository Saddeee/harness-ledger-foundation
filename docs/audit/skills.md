# Skills-capability audit (2026-09-18)

Scope: every layer of Harness Ledger that could touch Lovable's Skill primitive —
the Harness↔Lovable MCP client, the Lovable REST client, the SQLite schema, the
sync executor, the analysis/proposal pipeline, the Harness MCP server, and the
web UI. Read-only audit; no `mcp__lovable__*` / `mcp__harness__*` tool was
called; `cd harness && npm test` was run (all 734 tests pass) as the only live
command.

## 2. Evidence detail (selected, beyond the table)

- **The 8-tool allowlist is real and matches design intent.** `lovable-mcp.ts`'s `LovableReader`/`LovableWriter` interfaces (`lovable-mcp.ts:31-60`) and the single `call(name, args)` chokepoint (`lovable-mcp.ts:198-216`) mean every outbound MCP call is one of exactly 8 literal strings, all present in the file: `get_me` (226), `list_projects` (236), `list_messages` (244), `get_project_knowledge` (254), `get_workspace_knowledge` (258), `list_workspace_skills` (262-263), `set_project_knowledge` (268), `set_workspace_knowledge` (272). None of `get_workspace_skill`, `create_workspace_skill`, `update_workspace_skill`, `delete_workspace_skill` (the four extra tools your environment lists as existing in the orchestrator's Lovable MCP) appear anywhere in `harness/src`. This matches `docs/HANDOFF.md:33` ("Only eight Lovable tools are reachable by construction") and the explicit design note in `docs/superpowers/plans/2026-09-11-local-executor-and-knowledge.md:16`.

- **Lovable's REST API (via the SDK's OpenAPI types) does expose full Skill CRUD, but it is marked deprecated with "no replacement" for the workspace-skill write paths.** `node_modules/@lovable.dev/sdk/dist/index.d.ts:1966-2004` documents `GET/PUT/POST/DELETE /v1/workspaces/{workspace_id}/skills/{skill_name}` and `GET /v1/workspaces/{workspace_id}/skills`, every one annotated `@deprecated` with `"Deprecated compatibility endpoint. No replacement in the public API."`. The request/response bodies exist and are fully typed (`V1WriteWorkspaceSkillInputBody` — just `{ markdown: string }`, `V1WorkspaceSkillDTO`, `V1WriteWorkspaceSkillOutputBody` returning a `commit_sha`, `index.d.ts:5759-5775, 6018-6026`), so the SDK/API technically still accepts calls — but Lovable's own docs mark them a dead end for new integration work. This is why "create/update a Harness-managed Skill" is `unavailable` in Harness rather than merely `blocked`: Harness's own client code never attempts it, independent of whether Lovable would accept the call.

- **A *separate*, non-deprecated "project skill enable/disable" surface exists** (`GET /v1/skills?project_id=`, `PATCH /v1/skills/{skill_name}`, `index.d.ts:1244-1283, 8497-8560`) built around a different Skill shape (`V1ProjectSkillDTO`, skills living in a project's own repo, each with an `enabled: boolean`). This answers "does Lovable even have per-project skill enablement" — **yes**, but it is a different Skill concept (per-project repo skills) than the "workspace Skills" concept Harness reads (`V1WorkspaceSkillDTO`, one shared library per workspace, shown on the `/skills` page). Harness code has no awareness of project-level skills or their `enabled` flag at all.

- **The UI never actually offers "Skill" as a destination**, despite the backend Zod schema accepting the string. `src/components/harness/improvement.tsx:127` types the picker as `type Destination = "project" | "workspace"` (no `"skill"` member), and `ADD_LABELS` (`improvement.tsx:129`) only has `project`/`workspace` entries; the two rendered buttons are always `<AddConfirm destination="project">` / `<AddConfirm destination="workspace">` (`improvement.tsx:1109-1116, 1299-1305`). `harness/test/ux.test.ts:159` is a structural test titled "decision card: three buttons for pending items ... **no Skill**, no Decide later" and it passes (ok 701). `src/lib/harness-ux.ts:245-249`'s `DESTINATION_LABELS` map does carry `skill: "As a Skill"`, but it is dead code for the accept flow — it is only read via `label(DESTINATION_LABELS, destination)` where `destination` comes from `rule.scope` / `correction_candidates.proposed_scope`, both DB columns whose `CHECK` constraint excludes `'skill'` (`migrations.ts:116,156,170,213`), so this label can never actually render for a live rule/correction.

- **`npm test` (734/734 passing)** confirms every Skill-related test referenced above is green, not merely present: "snapshotSkills records changed skills only" (102), "...records a deleted skill..." (144), "...never marks skills deleted from an incomplete or malformed answer" (146), "lovable-mcp listWorkspaceSkills: complete only for a well-formed answer without has_more" (147), "buildTimeline: a workspace timeline includes two skill snapshots..." (215), "skill destination is rejected with a clear error" (278), "v5 skill snapshots dedupe by content and return latest per name" (429), "skills.tsx: heading, read-only line, per-skill fields, history, empty state" (500), "skills.ts: per-skill latest content plus full snapshot history with a line diff..." (521), "decision card: ... no Skill ..." (701), "no Knowledge write, no Skill write, no Lovable prompt is sent" (734, a structural guard over `store.ts`/`mcp-server.ts` source text).

## 4. Data model: is there a "destination"/"primitive" field, and a Skill-proposal model?

- **Yes, a `destination` field exists** and it is the *only* primitive-selection concept in the schema: `correction_candidates.proposed_scope` and `rules.scope`, both `CHECK (... IN ('project','workspace'[,'one_time']))` (`harness/src/migrations.ts:116,156,170,213`). It selects between the two Knowledge primitives (project Knowledge vs. workspace Knowledge) plus a non-primitive "one_time" (don't persist at all). It does **not** include `'skill'` at the database level, even though:
  - the API-layer Zod schema for `accept` optimistically accepts `destination: z.enum(["workspace","project","skill"])` (`improvements.ts:1039`) — an intentional "reject at the handler, not at parse time" pattern, per the explicit throw right after.
  - the front-end `DESTINATION_LABELS` map and MCP `resource_type` enum both carry a stray `"skill"` string (see §2/§3), suggesting the term was scaffolded early and never fully removed once the feature was descoped.
- **No Skill-proposal data model exists.** There is no table analogous to `correction_candidates`/`rules` for Skills — only `skill_snapshots`, which is a pure read-mirror (`workspace_id, name, description, content, sha256, updated_at_remote, fetched_at, fetched_by, deleted`, `migrations.ts:383`) with no `status`, no `proposed_by`, no `decision`, no link back to a correction or task episode.

## 5. Smallest complete Harness-managed Skill lifecycle: what it would need

To go from today's read-only mirror to a real, minimal "propose → approve → write → verify → version → retire" Skill lifecycle comparable to what exists for Knowledge, the smallest complete slice would need:

1. **Lovable client layer** (`harness/src/executor/lovable-mcp.ts` or a REST path in `lovable-rest.ts`):
   - Wire `create_workspace_skill` / `update_workspace_skill` (MCP) — these tools already exist in the orchestrator's Lovable MCP per the environment listing, so this is "un-restrict the allowlist + add typed wrappers", mirroring the existing `setProjectKnowledge`/`setWorkspaceKnowledge` pattern (`lovable-mcp.ts:268-272`). ~2–3 hours (wrapper + defensive field mapping + unit tests, following the `toSkill`/`skillListFromResponse` pattern already in the file).
   - Decide whether to also use `get_workspace_skill` for a pre-write existence/hash check (mirrors the "sha check before write" pattern in `executeWrites`, not seen in this audit's read of `beats.ts` but implied by the Knowledge write pipeline's `stale` handling). ~1 hour.
   - `delete_workspace_skill` only needed if "retire" must actually remove the Skill from Lovable rather than just mark it locally retired. ~1 hour.

2. **Schema** (`harness/src/migrations.ts`, `harness/src/store.ts`):
   - Add `'skill'` to the `rules.scope` and `correction_candidates.proposed_scope` `CHECK` constraints (a new migration, since SQLite can't `ALTER ... CHECK` in place — needs the table-rebuild pattern already used elsewhere in `migrations.ts`, e.g. the `round7_skill_deletions` migration at line 763 shows the file's own idiom for additive SQLite migrations). ~2 hours including a data-migration test.
   - A `skill_name` column (or a small `skill_targets` side table) somewhere a rule/correction can point at *which* Skill it proposes to create/edit, since a Skill is identified by `name` not by `(scope, project_id)` the way Knowledge targets are. ~2 hours.
   - A `knowledge_versions`-equivalent for Skills (or extend `knowledge_versions.target` to accept a Skill identity) to get staged/pending/written/stale/failed/cancelled status tracking for a Skill write, mirroring the existing Knowledge write-status machinery in `improvements.ts`. This is the single largest piece — realistically a fork of the whole pending-write / `executeWrites` beat, parameterized over "Knowledge vs Skill" targets. ~6–10 hours.

3. **Analysis / proposal pipeline** (`harness/src/analysis/propose.ts`):
   - Teach the Rule-writer prompt and its JSON schema (`propose.ts:91`) a `scope: "project"|"workspace"|"skill"` choice, plus guidance for *when* a correction is Skill-shaped (e.g. "a reusable multi-step technique/procedure" vs. "a standing preference") — this is a genuine prompt-design task, not just a schema change, since Knowledge and Skills solve different problems in Lovable's own product model. ~4–6 hours including eval against real correction transcripts.

4. **UI**:
   - Add `"skill"` back into `Destination` (`src/components/harness/improvement.tsx:127`) and a third `AddConfirm` button/flow; remove the dead `DESTINATION_LABELS.skill` landmine by actually wiring it up; a Skill-content editor (multiline markdown, since Skills are full `SKILL.md` files, not short instructions) somewhere in the accept/change-wording flow. ~4–6 hours.
   - Restore/retire actions extended to target `skill_snapshots` the way they target `knowledge_versions`/`rules` today. ~3–4 hours.

5. **Judge/adherence**: extending `rule_adherence`-style "was this Skill actually invoked/followed" observation is not achievable at all today because Lovable's MCP/REST surfaces give no signal of *skill invocation* during a build — only skill *content*. This would require either parsing Lovable chat replies for tool-use/skill-invocation markers (uncertain whether Lovable exposes this) or is simply out of scope. Flag as a research spike, not an estimate: **0.5–1 day of investigation before any implementation estimate is safe.**

**Total rough estimate for the smallest complete lifecycle (excluding the Judge/adherence research spike): ~25–35 hours**, dominated by the write-status/versioning fork (item 2c) and the analysis prompt work (item 3). This assumes Lovable's `create_workspace_skill`/`update_workspace_skill` MCP tools behave as documented and are not also headed toward the "deprecated, no replacement" fate their REST equivalents already carry (see Risks below) — worth confirming with Lovable before investing the schema/analysis work.

## 6. Risks

- **Workspace-wide blast radius.** A `V1WorkspaceSkillDTO`/`create_workspace_skill` write touches the shared workspace skill library (`node_modules/@lovable.dev/sdk/dist/index.d.ts:5759-5775`: "Skill name; matches the directory under `skills/` **in the workspace repo**") — there is exactly one such repo per workspace, shared by every project in it. Unlike Knowledge, which has a project-scoped variant, Harness has no way to write a Skill that only affects one project's build (project-level skills are a *different*, read-disabled-here concept — see §2). Any future Harness-authored Skill write is inherently workspace-wide and will affect every project the user (and possibly teammates) build in Lovable, immediately on write (`V1WriteWorkspaceSkillOutputBody.commit_sha` implies it commits straight to the workspace repo, no draft/preview state in the type).
- **The REST write path for workspace Skills is marked `@deprecated`/"no replacement" by Lovable itself** (`index.d.ts:1980,1986,1992` comments). Building on it risks building on a surface Lovable may remove; the MCP tools (`create_workspace_skill` etc., visible only in the environment's tool listing, not in this SDK file) may be the only forward-compatible path, and this audit could not verify their behavior without calling them (rule: never call).
- **No ownership signal exists to protect a user-authored Skill from being overwritten.** `skill_snapshots.fetched_by` records who *read* it into Harness, never who authored it in Lovable — there is nothing today (and nothing planned in the schema) that would let a future write path distinguish "a Skill Harness created and may safely update" from "a Skill the user wrote by hand in Lovable and Harness must never touch." This must be designed before any write capability ships, not after.
- **Dead-but-present "skill" tokens are a landmine for future contributors.** The Zod `destination` enum in `improvements.ts:1039`, the `DESTINATION_LABELS.skill` string in `harness-ux.ts:248`, and the `resource_type: "skill"` enum member in `store.ts:975`/`mcp-server.ts:398` all suggest "skill" was scaffolded once and then intentionally blocked at one layer (the `improvements.ts` throw, the missing `Destination` UI type, the missing DB `CHECK` value) rather than removed everywhere. A future change that touches only one of these layers (e.g. removing the throw without also updating the DB `CHECK`) would produce a confusing runtime failure rather than the current clean, explicit rejection.
- **No test coverage for a live Skill *write*** (only reads/sync are tested) — if the throw in `improvements.ts:1413` is ever removed, there is currently zero test scaffolding (fake `LovableWriter.setWorkspaceSkill`-equivalent, etc.) to build on; the existing `LovableWriter` interface (`lovable-mcp.ts:57-60`) would need a new method entirely.

## Summary (10 lines)

Harness Ledger's Skills support today is real but strictly read-only, and it knows it: `list_workspace_skills` is synced hourly into a deduped, versioned `skill_snapshots` table, surfaced on `/skills` and in the History timeline, all fully tested (734/734 tests pass). No code path anywhere — MCP client, REST client, analysis/proposal pipeline, or Harness's own MCP server — ever calls `create_workspace_skill`, `update_workspace_skill`, `delete_workspace_skill`, or their REST equivalents; the client's tool allowlist is hard-limited to 8 named tools by construction, matching the handoff doc's claim exactly. A `destination: "skill"` option exists in the accept-action's API schema and the UI's label map, but it is dead: the UI never renders a Skill button, and even a forced API call hits an explicit, tested error before reaching a DB `CHECK` constraint that also excludes `'skill'` — two independent walls, not one. Lovable's own SDK types show the workspace-skill REST write endpoints are themselves deprecated with "no replacement," a real risk for any future build-out, and reveal a second, separate "project skill" (`.agents/skills/`, per-project `enabled` flag) concept that Harness never reads at all. No Skill-proposal, versioning-of-proposal, restore, retire, evidence-link, replay-test, or adherence-observation model exists — those all remain Knowledge/rule-only concepts. All user-facing copy (README, `/skills` page) is accurate about the read-only state; the only latent misleading risk is the unused `DESTINATION_LABELS.skill` string. A minimal real write lifecycle is estimated at roughly 25–35 hours, dominated by forking the Knowledge write-status/versioning machinery and prompt-engineering the Rule writer to recognize Skill-shaped corrections, plus an unscoped research spike for any "was the Skill actually followed" observability. The single biggest structural risk of building this at all is that a workspace Skill write is shared across every project in the workspace with no draft/undo signal in the API and no ownership model to protect a user's own hand-written Skills.
